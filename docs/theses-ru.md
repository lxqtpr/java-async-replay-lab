# Кооперативный runtime для воспроизводимого тестирования асинхронной логики Java

**Гадельшин Даниил Маратович, Санкт-Петербургский политехнический университет Петра Великого.**

**Статус:** редактируемый черновик тезисов от 15.10.2026. Не подан и не принят к публикации. Научного руководителя, соавторов, контактные данные и окончательное оформление следует согласовать перед подачей. Этот текст описывает новый прототип; исторический отчёт о polling не заменяется и не считается его экспериментальной оценкой.

**Ключевые слова:** Java, асинхронное тестирование, виртуальное время, управляемое выполнение, replay, JUnit 5.

Асинхронная прикладная логика может нарушить инвариант из-за порядка событий даже без одновременного выполнения инструкций. Например, операция уже завершена по таймауту, но поздний callback всё ещё меняет состояние. Ожидание завершения future не выражает требования к такому эффекту. Для исследования ошибки требуется связать порядок событий, итоговое состояние и повтор конкретного исполнения. В работе рассматривается ограниченный вопрос: можно ли сделать эту связь проверяемой для логики, явно использующей внедряемые часы и исполнитель задач?

Подход развивается на основе прежнего учебного расширения JUnit 5 с ожиданием условий и управлением ресурсами. Polling и lifecycle отделены от нового механизма: они не управляют расписанием потоков. Управляемые планировщики уже существуют. [jMock](https://jmock.org/threading-scheduler.html) документирует виртуальную временную шкалу; [Awaitility](https://github.com/awaitility/awaitility/wiki/Usage) — ожидание условий с настраиваемым polling; [Lincheck](https://github.com/JetBrains/lincheck) — исследование конкурентных чередований JVM и воспроизводимые трассы. Поэтому новизна детерминированного тестирования в целом не заявляется. Вклад работы — связанный прототип с явными ограничениями, небольшим корпусом и проверкой повторения прикладных исходов.

Реализованный `ControlledRuntime` предоставляет `Clock`, `Executor` и отложенные задачи. Все callback выполняются последовательно в создавшем runtime потоке. Сначала выбирается ближайший deadline, затем seed определяет выбор среди задач с одинаковым сроком. Внутри callback переключения не моделируются. Тест может выполнить один шаг, продвинуть виртуальное время или обработать очередь с бюджетом. Адаптер JUnit 5 выдаёт отдельный runtime каждому тесту и считает оставшиеся задачи ошибкой завершения.

Trace фиксирует время вызова, доступные идентификаторы задач, выбранные ID и label, нормальный исход либо класс исключения. Replay проверяет соответствие решений и полноту журнала. Это не снимок состояния приложения: постановки задач и отмены создаются сценарием заново, а прикладной результат проверяет отдельный оракул. Изменение сценария может сделать trace несовместимым. Для надёжной диагностики повтор должен сохранять сигнатуру нарушения, а не только класс исключения.

Корпус содержит четыре вручную сконструированных сценария с ошибочной и исправленной версиями. `timeout-late-effect` проверяет отсутствие эффекта после победившего таймаута и один эффект при успешном завершении. `unknown-result-retry` моделирует уже выполненную, но ещё не подтверждённую операцию: стабильный ключ предотвращает второй эффект реально поставленного повтора. `cancel-retry` отделяет отмену исходной попытки от новой, которая должна выполнить полезную работу. `callback-after-close` запрещает запись после закрытия, сохраняя запись в ещё открытый ресурс. Все эффекты представлены состоянием памяти; атомарная дедупликация является предположением модели.

В эксперименте использованы seed 0–31 для каждой пары сценарий/версия и бюджет 100 callback на запуск. Прикладные события происходят не позднее второй виртуальной секунды, завершающий оракул — на четвёртой. Для каждого запуска сохраняется сырая запись и trace, который читается с диска для повторного исполнения свежей копии сценария. Исправленные версии дополнительно проверяются на положительных ветвях, чтобы прохождение не достигалось подавлением всей работы. Seed представляет вариант выбора порядка, а не независимый найденный дефект. Уникальные пути dispatch подсчитаны отдельно по решениям trace без seed.

Локальные кампании на Oracle JDK 25.0.2 и Amazon Corretto 21.0.10 дали одинаковые сводные результаты. В каждой получено 256 записей: 182 прохождения оракула и 74 проявления ожидаемых дефектов. Для buggy нарушения составили соответственно 21/32, 21/32, 11/32 и 21/32 в порядке перечисленных сценариев. Все 128 fixed-исполнений прошли проверку, все 256 replay сохранили сигнатуру, итоговое состояние и trace. Неожиданных ошибок не зарегистрировано. При этом в каждой из восьми групп сценарий/версия обнаружено только два уникальных пути: 32 seed повторяют небольшую развилку. Полный набор из 34 тестов прошёл на обоих JDK при компиляции `--release 17`.

Сырые CSV, environment с командами, SHA-256 исходников и сохранённые trace находятся в [research-results](../research-results/). [Отдельный контрольный анализ](../research-results/analysis.json) фиксирует результаты пересчёта показателей и побайтового сравнения 256 соответствующих trace между двумя JDK. Это наблюдение ограничено данным корпусом и версией кода. Время runner включает файловое I/O и повтор, поэтому производительность инструментов по нему не сравнивается.

Главное ограничение — ручной подбор небольшого корпуса под поддержанную кооперативную модель. Runtime не контролирует произвольные потоки, JMM, общий пул, реальные часы и внешнее I/O. Бюджет ограничивает число callback, но не прерывает блокировку внутри них. Повтор одного пути не устанавливает полноту поиска, а доля нарушений по seed не является универсальной оценкой эффективности. Реальные baseline и независимая репликация пока отсутствуют; превосходство над библиотеками и промышленная готовность не утверждаются.

Работа предоставляет основу для ограниченной корпусной демонстрации и проверки replay. Дальнейшее исследование требует независимой проверки оракулов, сценариев из прикладного кода и сопоставимого baseline на одинаковых границах управления. Стоимость адаптации, неподдержанные случаи и отрицательные результаты следует учитывать наряду с найденными нарушениями.
