# Воспроизводимое тестирование асинхронной логики Java в кооперативной модели выполнения

**Гадельшин Даниил Маратович, СПбПУ.** Технический отчёт по локальному исследовательскому прототипу Java Async Replay Lab. Редактируемый черновик от 15.10.2026; перед подачей требуется авторская проверка текста, соавторства, прав на код и требований конкретной конференции. Публикация или принятие работы не заявляются.

## 1. Проблема и постановка задачи

В Java/backend результат асинхронной операции часто зависит от порядка нескольких событий: завершения запроса, таймаута, повторной попытки, отмены или закрытия ресурса. Даже при последовательной обработке callback возможна логическая ошибка. Например, таймаут уже определил результат операции, а позднее завершение всё ещё публикует побочное действие. Проверка только факта завершения future недостаточна: нужен инвариант, связывающий результат операции с изменением состояния.

Прежний учебный проект объединял ожидание условия, управление тестовыми ресурсами и очистку состояния в расширении JUnit 5. Сохранённые исторические отчёт и тезисы описывают polling и lifecycle; это исходная инженерная работа, но не реализация виртуального времени или replay. Новый прототип рассматривается отдельно. Исторические количественные результаты не переносятся на новую модель. Ссылки на исходные документы приведены в разделе источников.

Исследовательский вопрос сформулирован узко: позволяет ли небольшой runtime с внедряемыми часами и исполнителем воспроизвести нарушение заданного инварианта и повторить тот же диагностический исход на явно описанном корпусе? Рассматривается логика, которая передаёт все исследуемые callback в контролируемый исполнитель. Произвольное поведение JVM, межпоточные гонки памяти и внешние системы в постановку не входят.

## 2. Связанные работы и границы вклада

Виртуальное время, управляемое планирование и воспроизводимые исполнения уже используются в существующих инструментах. Поэтому вклад этой работы состоит в реализации и проверяемом описании ограниченного прототипа, корпуса и процедуры повторения, а не в изобретении детерминированного тестирования.

Документация [jMock DeterministicScheduler](https://jmock.org/threading-scheduler.html) описывает виртуальную временную шкалу, продвижение времени тестом и выполнение запланированных задач. Она отдельно оговаривает неподдержанные синхронные блокирующие методы и необходимость согласовать используемые приложением часы с планировщиком. Это ближайший пример по границе внедряемого исполнителя и времени. Для содержательного сравнения необходимы одинаковые сценарии и инварианты; совпадение назначения само по себе не доказывает эквивалентность семантики выбора задач.

[Awaitility](https://github.com/awaitility/awaitility/wiki/Usage) предоставляет DSL ожидания условий и утверждений с временным бюджетом и настраиваемым polling. Его документированный контракт полезен для наблюдения за асинхронным приложением. В данном исследовании требуется дополнительно задавать порядок контролируемых callback и сохранять решения планировщика. Это различие проверяемых возможностей, а не утверждение о худшем качестве ожидания или невозможности использовать Awaitility совместно с другими средствами.

Актуальный [Lincheck](https://github.com/JetBrains/lincheck) исследует чередования потоков JVM и предоставляет воспроизводимые трассы. Его README описывает как тестирование произвольного конкурентного кода, так и специальный API для структур данных со stress testing и bounded model checking. Ограничивать Lincheck только структурами данных было бы неверно. Наш runtime существенно уже: он не исследует выполнение внутри callback и не подменяет инструмент работы с реальными конкурентными операциями.

Статья [FoundationDB, SIGMOD 2021](https://www.foundationdb.org/files/fdb-paper.pdf) описывает детерминированную симуляцию взаимодействующих процессов и отказов диска, сети и запросов. Здесь заимствуется исследовательский принцип явного контроля источников неопределённости; масштаб и достоверность промышленного симулятора этому небольшому Java-прототипу не приписываются.

Практический пробел именно этого проекта — отсутствие связанного воспроизводимого пути от сценария и прикладного инварианта к сырой строке эксперимента, сохранённому trace и повторной проверке исхода. Прототип закрывает этот локальный пробел в кооперативной модели. Сравнительный эксперимент с перечисленными библиотеками пока не выполнен, поэтому превосходство, ускорение и более полное обнаружение ошибок не заявляются.

## 3. Архитектура прототипа

Ядро `ControlledRuntime` одновременно предоставляет `Clock`, `Executor` и API отложенного планирования. Оно привязано к создавшему его потоку. Часы начинаются с заданного origin; очередь содержит deadline, последовательный идентификатор, метку и callback. Сначала выбирается ближайший deadline. Из задач с одинаковым deadline выбор выполняется генератором, инициализированным seed. Callback выполняется целиком и может запланировать следующие задачи. Внутри callback переключений модели нет.

Метод `runNext` выполняет один шаг. `drain` обрабатывает очередь с бюджетом числа шагов, включая будущие таймеры. `advanceBy` ограничивает обработку заданным виртуальным интервалом. Отмена удаляет ожидающую задачу. Бюджет останавливает бесконечное перепланирование между callback, но не способен прервать блокировку внутри уже вызванного callback; для такого кода требуется отдельная защита тестового процесса.

Trace содержит виртуальное время каждого вызова, идентификаторы доступных задач, выбранные ID и label, а также нормальный исход либо класс исключения. При replay проверяются эти сведения и полнота потребления записанных решений. Все постановки задач, отмены и состояния сценарий создаёт заново: trace не является полным журналом приложения. Он не сохраняет снимки памяти, значения всех результатов, сообщения исключений или внешнее I/O. Совместимость trace после изменения кода не гарантируется.

Адаптер JUnit 5 создаёт отдельный runtime для теста и предоставляет его через внедрение параметра. Незавершённые задачи при teardown считаются ошибкой; они не выполняются молча. Прежние модули ожидания и агрегации CSV сохранены отдельно. Новая проверка не выдаёт их за часть механизма управления расписанием. Первичный источник архитектурных утверждений — [код ядра](../async-replay-core/src/main/java/dev/asyncreplay/ControlledRuntime.java), [формат trace](../async-replay-core/src/main/java/dev/asyncreplay/RunTrace.java) и [адаптер](../async-replay-junit5/src/main/java/dev/asyncreplay/junit5/AsyncReplayExtension.java).

## 4. Корпус сценариев и прикладные оракулы

Четыре сценария реализованы в [ScenarioCorpus.java](../async-replay-core/src/main/java/dev/asyncreplay/corpus/ScenarioCorpus.java). Каждый имеет ошибочную и исправленную версии, собственное состояние и завершающий оракул. Одинаковый deadline моделирует точку неопределённости порядка. Это специально сконструированные логические примеры, а не четыре найденных дефекта промышленного проекта.

| ID | Ошибка и исправление | Проверяемое условие |
|---|---|---|
| `timeout-late-effect` | Completion публикует эффект независимо от победителя; исправление допускает эффект только при успешном завершении ещё ожидающей операции | Timeout означает ноль эффектов; успешное завершение означает ровно один |
| `unknown-result-retry` | Повтор после уже выполненной, но ещё не подтверждённой операции получает новый ключ попытки; исправление сохраняет ключ логической операции | Результат в итоге известен, попытка выполнена, эффект ровно один |
| `cancel-retry` | Запоздалая отмена обращается к изменяемому `current` и отменяет новую попытку; исправление захватывает handle исходной попытки | Исходная попытка не создаёт эффект, новая попытка завершается и создаёт один эффект |
| `callback-after-close` | Callback записывает в уже закрытый логический ресурс; исправление проверяет состояние перед записью | Нет записи после закрытия; callback открытого ресурса выполняет полезную запись |

В первом сценарии timeout и completion назначены на первую виртуальную секунду. Во втором первоначальный эффект выполняется в нулевой момент, а подтверждение соревнуется с таймером повтора на первой секунде. Если повтор поставлен, последующее подтверждение его не отзывает. В третьем отмена исходной попытки соревнуется с созданием новой. В четвёртом закрытие соревнуется с completion. Все прикладные callback завершаются не позднее второй секунды модели, а оракул запускается на четвёртой: он проверяет состояние после исследуемых действий.

Исправленная версия не должна проходить тест за счёт удаления всей работы. Поэтому [контрактные тесты корпуса](../async-replay-core/src/test/java/dev/asyncreplay/ScenarioCorpusTest.java) требуют положительных ветвей: успешного completion, реально выполненного и дедуплицированного повтора, завершившейся новой попытки и записи до закрытия. В модели дедупликация и применение эффекта атомарны по предположению последовательного исполнения. Реальную транзакцию, сетевую отмену или корректность при параллельной проверке флага эти сценарии не доказывают.

## 5. Методика и бюджет эксперимента

Единица наблюдения — запуск конкретной пары сценарий/версия с конкретным seed. Выполнены четыре сценария, две версии и набор seed от 0 до 31. Новый runtime создаётся для каждого запуска, origin фиксируется, состояние между запусками не переносится. Бюджет обработки составляет 100 callback на запуск. Завершение с нарушением прикладного инварианта отделяется от ошибки инфраструктуры, исчерпания бюджета и расхождения replay.

Кампании выполнены локально на Oracle JDK 25.0.2 и Amazon Corretto 21.0.10, Mac OS X 26.6.2, aarch64. Компиляция использует `--release 17`; исполнение на JDK 17 не проверено. На каждом JDK получено 256 исходных записей и выполнено по одному replay каждой записи. Таблица показывает результат одной кампании; показатели второй совпали. Столбец replay включает buggy и fixed, а столбец путей показывает число разных последовательностей dispatch отдельно для каждой версии.

| Сценарий | Buggy: нарушения / запуски | Fixed: нарушения / запуски | Согласованный replay / проверок | Уникальные пути buggy / fixed |
|---|---:|---:|---:|---:|
| `timeout-late-effect` | 21 / 32 | 0 / 32 | 64 / 64 | 2 / 2 |
| `unknown-result-retry` | 21 / 32 | 0 / 32 | 64 / 64 | 2 / 2 |
| `cancel-retry` | 11 / 32 | 0 / 32 | 64 / 64 | 2 / 2 |
| `callback-after-close` | 21 / 32 | 0 / 32 | 64 / 64 | 2 / 2 |
| **Всего** | **74 / 128** | **0 / 128** | **256 / 256** | **по 2 в каждой из 8 групп** |

В каждой кампании 182 исходных исполнения прошли оракул, 74 проявили ожидаемый дефект buggy. Все 128 fixed-исполнений прошли проверку. Неожиданных ошибок runner и расхождений replay не зарегистрировано. Положительные ветви исправлений также проверены контрактными тестами. Полный Maven-набор содержит 34 теста: 26 ядра, 4 адаптера JUnit и по 2 сохранённых extension и CSV-агрегатора. На обоих JDK нет ошибок, сбоев и пропусков. Эти 34 теста и 256 записей кампании — разные единицы учёта.

После основного исполнения trace сохраняется на диск, загружается заново и применяется к новой копии того же сценария. Прикладная сигнатура имеет стабильный вид `scenario:invariant`. Совпадения одного класса исключения недостаточно: runner проверяет равенство сигнатуры нарушения, итогового состояния и полного trace, включая потребление решений. Для успешных исполнений также нужен согласованный исход. CSV содержит `scenario`, `variant`, `seed`, `outcome`, `failure_signature`, `state`, `steps`, `trace_bytes`, `replay_match`, `wall_nanos`. Нарушение оракула в buggy помечается `EXPECTED_BUG`; такая строка означает ожидаемое проявление дефекта модели, а не сбой runner. Неожиданная ошибка прерывает кампанию и фиксируется в summary, поэтому незавершённый CSV нельзя считать полным успешным прогоном.

Измеряемое число нарушений относится только к данному набору расписаний. Seed задаёт выбор при равных deadline, а не независимый промышленный дефект. Для каждой пары сценарий/версия подсчитаны уникальные пути dispatch: сравнивается последовательность решений trace без заголовка с seed. Получено ровно два пути в каждой из восьми групп. Основная развилка состоит из двух callback с одинаковым deadline, поэтому 32 seed многократно повторяют эти порядки. Отношение нарушений к числу запусков не интерпретируется как общая вероятность обнаружения ошибок. `wall_nanos` включает запись, файловое I/O и replay; это диагностическое время, которое не используется для сравнений производительности.

Сохранены [CSV JDK 25](../research-results/jdk25/raw.csv), [CSV JDK 21](../research-results/jdk21/raw.csv), summary, environment и отдельные trace для каждого запуска. [Контрольный анализ](../research-results/analysis.json) фиксирует результаты проверки строк, размеров, покрытия групп и пересчёта исходного fingerprint. SHA-256 исходного набора на обоих JDK: `6efa674b1321c9e6155a39806e8466833b198ce666b2170b3939969124dc1d9a`. Fingerprint охватывает Java, XML, shell и properties, исключая документацию и данные. Все 256 соответствующих файлов trace оказались побайтово идентичны между JDK 21 и 25. Это локальный результат для данной версии и корпуса, а не гарантия для всех JVM.

Фактические команды и версии записаны в [environment JDK 25](../research-results/jdk25/environment.json) и [environment JDK 21](../research-results/jdk21/environment.json). Для повтора из корня репозитория используются `sh scripts/verify.sh -o` и `sh scripts/run_corpus.sh research-results/reproduce-jdk25 32` с новым пустым выходным каталогом и выбранным JDK в окружении. Для второго JDK следует согласованно выбрать `java` и `javac`, при необходимости через `JAVA_BIN` и `JAVAC_BIN`. Runner отказывается смешивать результаты с существующим непустым каталогом.

## 6. Ограничения достоверности и воспроизводимость

Основная угроза внешней достоверности — ручной подбор корпуса. Сценарии и исправления созданы под поддержанную границу runtime; наблюдение ожидаемого результата не показывает пригодность для произвольного Java/backend. Внутренняя достоверность зависит от правильности оракулов и самого планировщика. Проверка runtime, сериализации и отказов replay снижает этот риск, но не является независимой формальной верификацией. Автор корпуса и автор проверяемого механизма находятся в одном процессе разработки; независимая репликация пока отсутствует.

Ограниченный набор seed не покрывает всё пространство программ. Внутреннее выполнение callback считается неделимым; загрузка процессора, JMM, блокировки, общий пул, часы ОС, сеть и база данных не контролируются. Счётчики эффектов — состояние памяти модели. Положительный результат для дедупликации нельзя переносить на раздельные операции «проверить ключ» и «записать» в настоящем хранилище.

Для воспроизведения необходимо использовать одну версию исходников, зафиксированные команды и полный набор артефактов. Сначала запускаются контрактные тесты, затем корпус с указанным бюджетом, после чего независимо пересчитываются сводные показатели из CSV и проверяются сохранённые trace. Смена JDK или кода требует нового прогона. Подготовленная CI-конфигурация сама по себе не подтверждает успешный удалённый запуск. Проверки Docker/PostgreSQL из прежнего demo не включаются в результаты кооперативного корпуса без отдельного запуска.

## 7. Выводы и дальнейшая работа

Реализован ограниченный механизм управления виртуальным временем, выбора между callback с одинаковым deadline и сохранения решений для replay. Корпус задаёт четыре разных прикладных инварианта и полезные ветви исправленных версий. В обеих локальных кампаниях проявились все четыре сконструированных дефекта, исправленные варианты прошли оракулы, а каждое сохранённое исполнение было согласованно повторено. Утверждения об общей эффективности, превосходстве библиотек и промышленной готовности из данной постановки не следуют.

Следующий исследовательский шаг — независимая проверка сценариев, расширение корпуса на реальные фрагменты прикладной логики и согласованный baseline, прежде всего с jMock для совместимых границ. Следует отдельно учитывать стоимость внедрения зависимостей и несовместимые случаи. Исторический polling-проект остаётся источником инженерного контекста, но новая модель требует собственных результатов и собственного отчёта.
